## Question

`sdip ingest` peaks at 1,008.6, 2,199.6 and 5,528.1 MB on 0.40, 1.60 and 4.81 GB sources,
1.03 MB per MB (P23, P26). **Stage A:** which stage of ingest sets that peak, and is it SDIP's
code or `multidimio`'s `segy_to_mdio`? **Stage B** (criteria by amendment): if the stage is
SDIP's, does reading it block by block bound the peak, with the store unchanged? If it is
upstream's, the fit is recorded as the limit (D-0130) and stage B does not run.

## Fixtures

P23's two files, regenerated by the same committed generator call. Each must hash to P23's
recorded sha256, or the run stops:

| Name | Generator | sha256 |
|---|---|---|
| `small` (0.40 GB) | `make_poststack3d(n_inline=150, n_crossline=630, n_samples=1000)` | `ac6001f6…927ca03a` |
| `large` (1.60 GB) | `make_poststack3d(n_inline=600, n_crossline=630, n_samples=1000)` | `2b8b7aa0…1cd3eb2e` |

Both are `ibm32`, so the raw sample view is written.

## Stage A method

At `main` `077c8e6` plus this registration, with no code change. Each fixture is ingested once
with `/usr/bin/time -l sdip ingest` (the whole command; peak from `maximum resident set size`).
Then each stage below runs **alone in a fresh Python process**, built from the default
declaration as `sdip ingest` builds it, and prints `resource.getrusage(RUSAGE_SELF).ru_maxrss`
(bytes on macOS) as its last act:

| Stage | What it runs | Where |
|---|---|---|
| `baseline` | imports and the declaration only | — |
| `preflight` | `validate_source(source, declaration)` | — |
| `hash` | `sha256_file(source)` | — |
| `g1` | `declaration.build_spec()` and `g1_for_spec` | — |
| `file_headers` | `read_raw_file_headers` and `classify_textual_header` | — |
| `convert` | `segy_to_mdio` with the spec, template and persistence mode `ingest_declared` uses | a fresh store path |
| `axis_origin` | the source headers read and `decide_for_store`, as `ingest_declared` does it | the ingested store, read only |
| `raw_samples` | `attach_raw_sample_view` | the ingested store, rewritten in place |
| `header_plane` | `attach_header_plane` | the ingested store, rewritten in place |
| `marker` | `attach_provenance_marker` | the ingested store, rewritten in place |

`convert` runs without SDIP's warning and log recorders around it. They hold records, not
arrays, so they are not expected to move the peak; criterion 2 reports whether the isolated
stages account for the whole command. The driver's source is recorded in the receipt.

## Stage A criteria

1. **Reproduces P23.** The whole-command peak on `large` is reported next to P23's
   (2,199.6 MB). A difference of more than 10 % is reported as a reproducibility finding
   before anything is attributed.
2. **Attributes the peak.** The stage with the highest isolated peak on `large` is named. If
   its peak is at least 90 % of the whole-command peak, it **sets** the peak. If no stage
   reaches 90 %, the peak comes from memory held **across** stages, and that is the finding
   stage B must address instead.
3. **Attributes the growth.** For each stage, `(peak_large − peak_small)` in MB per MB of
   source is reported, so the stages that grow with the file are named.
4. **Names the owner.** If the stage that sets the peak is `convert`, the peak is
   upstream's: recorded as the limit, and stage B does not run. Otherwise it is SDIP's.

Stage A changes no code and gates nothing.

## Stage B (outline only; criteria by amendment)

Read the stage stage A names block by block, as P24 did for Plane 3. Every array the store
holds must stay byte-identical to the stage A store, measured by each array's sha256 over its
decoded bytes, and the whole default gate must pass. The amendment states before any
measurement:
- the scope;
- the bound on `large`'s peak;
- the bound on the slope;
- the store-identity check.

## Not in this probe

The 7.2 GiB ingest envelope stays until stage B's result is ruled on. Prestack geometries,
non-`ibm32` sources (no raw sample view), real survey data and the `certify` chain are not
measured.

- **Criterion 1 (reproduces P23): holds.** 2,368.4 MB against P23's 2,199.6 MB, 7.7 % apart.
- **Criterion 2 (attributes the peak): `raw_samples` sets it**, at 90.7 % of the whole
  command. `header_plane` is at 86.7 %, so it would set nearly the same peak alone.
- **Criterion 3 (attributes the growth):** `raw_samples` and `header_plane` grow at 1.15 MB per

  grows at 0.03.
- **Criterion 4 (names the owner): SDIP.** `convert` is 7.4 % of the peak. Stage B runs.

**What this means.** Both stages read the source through a memory map
(`read_source_words`, `read_source_header_bytes`) and index every trace, so nearly every page of
the file becomes resident. That is the cause P24 found in verify's Plane 3. On these fixtures
the raw sample view stores **0 entries**, so none of `raw_samples`' 2.1 GB is data it keeps.
`ru_maxrss` counts this process only: upstream's worker processes are outside both the stage
and the whole-command numbers, as in P23 and P26.

## Amendment B, 2026-11-05 — stage B criteria, before any stage B code is measured

**Scope.** `attach_raw_sample_view` reads each outermost slab's live source words with
`read_source_words_at`, and `attach_header_plane` each slab's live header bytes with
`read_source_header_bytes_at`. Both are the explicit-read functions verify has used since
D38, at the same offsets as the mapped readers they replace. Nothing else changes: the parsed
source headers (0.24 MB per MB) stay as they are.

**Criteria**, measured as stage A was, on the same fixtures:
1. **Peak.** The whole `sdip ingest` on `large` peaks at **1,200 MB or less**.
2. **Slope.** The whole command grows at **0.40 MB per MB or less** between `small` and `large`.
3. **Store identity.** On both fixtures, every array's sha256 over its decoded bytes, and its
   attributes' sha256, equal stage A's (in the receipt). One difference fails the stage.
4. **Gate.** The default suite, `ruff` and `mypy` pass.

A failed bound stands failed, as P23's did, and is reported. The 7.2 GiB ingest envelope stays
until the result is ruled on.
