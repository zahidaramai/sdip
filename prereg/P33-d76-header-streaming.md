## Question

After P28, the parsed source headers alone grow at 0.2381 MB per MB of source (P28 stage A,
`axis_origin`). Ingest reads them whole up to three times:
- for the axis-origin decision;
- for the raw sample view's trace map;
- for the header plane's trace map.

**Stage A:** how much of the growth is the parsed header array, and how much is the trace map
built from it? **Stage B** (criteria by amendment): does reading only the needed header columns,
block by block through `segy`'s public slicing, remove the array's share, with the store
unchanged?

## Fixtures

P23's `small` (0.40 GB) and `large` (1.60 GB), regenerated by the committed generator and
hash-checked against P23's sha256, or the run stops.

## Stage A method

At this registration's commit, with no code change. Each step runs **alone in a fresh Python
process** with the default declaration's spec. It prints `ru_maxrss` (bytes, macOS) as its last
act:

| Step | What it runs |
|---|---|
| `baseline` | imports and the spec only |
| `headers_whole` | `SegyFile(source, spec).header[:]`, as ingest reads it today |
| `columns_blocked` | `header[i:i + 65,536]` over the file, keeping only `inline`, `crossline`, `delay_recording_time` and `times_scalar`, concatenated |
| `map_from_whole` | `headers_whole`, then `build_trace_map` against the ingested store's grid |
| `map_from_columns` | `columns_blocked`, then `build_trace_map` on those columns |
| `axis_origin_now` | `headers_whole`, then `decide_for_store`, P28's stage, re-measured |

**Equality check, before any memory is read:** `columns_blocked`'s four columns equal
`headers_whole`'s by `np.array_equal`, and `map_from_columns` gives the same `ordinal_to_cell`,
`cell_to_ordinals` and `unmapped` as `map_from_whole`. A difference stops stage A and is
reported. A cheaper read that gives a different answer is not a cheaper read.

## Stage A criteria

1. **Reproduces P28.** `axis_origin_now`'s slope is reported next to P28's 0.2381. More than
   25 % apart is reported as a reproducibility finding before anything is attributed.
2. **Attributes the term.** For each step, `(peak_large − peak_small)` in MB per MB:
   - the array's share is `headers_whole` minus `baseline`;
   - the trace map's share is `map_from_columns` minus `columns_blocked`.
3. **Names stage B's scope.** The share that is at least half of 0.2381 is stage B's target. If
   the trace map's share is at least that large, stage B must address the map too. The
   amendment says how, and no code is written before it.

Stage A changes no code and gates nothing.

## Stage B (outline only; criteria by amendment)

`sdip ingest` reads only the header columns each stage needs, in blocks, through `segy`'s
public `header` slicing. Scope:
- the axis origin needs the delay and its scalar;
- the trace maps need the grid's index fields;
- the trace map's own representation is in scope only if stage A names it.

Every array the store holds must stay byte-identical, by each array's decoded-bytes sha256 and
its attributes' sha256, measured on the stage A store less `statsV1.sumSquares`, the one key
P31 measured varying between ingests. The whole default gate must pass. The amendment states,
before any measurement:
- the bound, from stage A's numbers and P28's only;
- an **unseen** source size it is tested at;
- the identity check.

## Not in this probe

`verify`'s own trace map (the "P27" growth, D-0129) is not changed. The ingest envelope is
re-derived only if stage B passes, by its amendment. Prestack, real data and the `certify`
chain are not measured.

## Amendment B, 2026-11-05 — stage B criteria, before any stage B code is measured

**Scope.** In `sdip ingest`, the three whole reads of the source headers become blocked reads of
only the columns each stage uses, through `segy`'s public `header[i:j]` slicing in blocks of
65,536 traces:
- the axis origin reads `delay_recording_time` and `times_scalar`;
- the raw sample view's and the header plane's trace maps read the grid's index fields.

The trace map itself is unchanged. Nothing else changes.

**The bound, from stage A's and P28's numbers only.** What remains growing is the trace map's
**0.0871 MB per MB** (stage A). The fixed term is the larger of `peak − 0.0871 × size` over P28
stage B's two whole-command points: **966.83 MB**. The margin is 1.10, as P32's. That gives
**`B(S) = 1.10 × (966.83 + 0.0871 × S)` MB.** Those points still carry the header term, so this
fixed term is an overestimate, and that is its safe side.

**Criteria**, the whole `sdip ingest` under `/usr/bin/time -l` at stage B's code:
1. **The measured sizes:** at most `B(S)` on `small` (1,101.9 MB) and on `large` (1,217.1 MB).
2. **An unseen size, the gate.** `xxxl` is 18 pieces built the P32 way (piece `k` =
   `make_poststack3d(n_inline=300, n_crossline=630, n_samples=1000, inline_start=100 + 300 k)`,
   `k` = 0..17): **14,424,483,600 B**, never ingested. It is ingested once with `--envelope-gib
   14.0`, the raise for that run only, recorded. Its peak must be at most
   **`B` = 2,445.5 MB**.
3. **Store identity.** On `small` and `large`, every array's decoded-bytes sha256 and attribute
   sha256 equal stage A's stores (hashes in the receipt). Both sides are taken without
   `statsV1.sumSquares`, the one key P31 measured varying.
4. **Gate.** The default suite, `ruff` and `mypy` pass.

**If 1 to 4 hold:** the ingest envelope becomes `B`. Its default is where `B` reaches 8 GiB,
73.2 GiB, **capped at verify's 40.1 GiB**, because `certify` runs both. That makes **40.1 GiB**.
If any criterion fails, it stands failed, and 26.9 GiB stays.
