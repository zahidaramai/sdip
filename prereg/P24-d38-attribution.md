## Question

After P23, `sdip verify` on a 1.60 GB source still peaks at 2.25 GB, and memory still grows
with the file at 1.04 MB per MB of source. **Stage A:** which step of `verify` sets that peak,
and how does each step grow with the file? **Stage B** (criteria by amendment): does streaming
the reads stage A names bound the peak, with nothing reported changed?

## Fixtures

P23's two files, regenerated by the same committed generator call. Each must hash to P23's
recorded sha256, or the run stops:

| Name | Generator | sha256 |
|---|---|---|
| `small` (0.40 GB) | `make_poststack3d(n_inline=150, n_crossline=630, n_samples=1000)` | `ac6001f6…927ca03a` |
| `large` (1.60 GB) | `make_poststack3d(n_inline=600, n_crossline=630, n_samples=1000)` | `2b8b7aa0…1cd3eb2e` |

Each is ingested once with `sdip ingest`, at `main` `0c1edbc`.

## Stage A method

At `main` `0c1edbc`, with no code change. For each fixture, each step below runs **alone in a
fresh Python process**. Each process imports `sdip`, builds the default declaration, and runs
only that step, so its peak is that step's plus the interpreter's. The process's peak RSS is
read from `resource.getrusage(RUSAGE_SELF).ru_maxrss` (bytes on macOS) as its last act:

| Step | What it runs |
|---|---|
| `baseline` | imports and the declaration only |
| `binding` | `check_binding(store, declaration)` |
| `preflight` | `validate_source(source, declaration)` |
| `g1` | `declaration.build_spec()` and `g1_for_spec` |
| `plane_1` … `plane_5` | each plane function, with the spec built as `verify` builds it |
| `trace_map` | the source headers read and `build_trace_map`, as Plane 4 does it |
| `store_digest` | `check_store_digest(store)` |
| `content_digest` | `check_content_digest(store)` |

The whole command is also measured, as P23 did: `/usr/bin/time -l sdip verify --json
--skip-portability --envelope-gib 0`. The driver's source is recorded in the receipt.

## Stage A criteria

1. **Reproduces P23.** The whole-command peak on `large` is reported next to P23's after-value
   (2,253,045,760 B). A difference of more than 10 % is reported as a reproducibility finding
   before anything is attributed.
2. **Attributes the peak.** The step with the highest isolated peak on `large` is named. If its
   peak is at least 90 % of the whole-command peak, it **sets** the peak. If no step reaches
   90 %, the peak comes from memory held **across** steps, and that is the finding stage B must
   address instead.
3. **Attributes the growth.** For each step, `(peak_large − peak_small)` in MB per MB of source
   is reported, so the steps that grow with the file are named.

Stage A changes no code and gates nothing. Its numbers are the input to stage B's amendment.

## Stage B (outline only; criteria by amendment)

Stream the reads stage A names, with the same constraints as P23. The comparisons stay
`np.array_equal` and exact bytes, every reported value stays the same, and the whole default
gate must pass. The amendment states before any measurement:
- the scope;
- the bound on `large`'s peak;
- the bound on the slope;
- that the verify JSON must be byte-identical to the stage A run's.

## Not in this probe

The 1.0 GiB `--envelope-gib` default stays (D-0125). The whole `certify` chain, G4, ingest
memory, real survey data, and prestack geometries are not measured.

Peak RSS, each step alone in a fresh process (`ru_maxrss`), and the whole command
(`/usr/bin/time -l`):

| Step | `small` (0.40 GB) | `large` (1.60 GB) | MB per MB of source |
|---|---:|---:|---:|
| baseline (imports) | 57.1 MB | 56.7 MB | 0.00 |
| binding, preflight, g1, plane 1, plane 2, both digests | 56–67 MB each | 56–67 MB each | 0.00 |
| **plane 3** | 630.3 MB | **2,254.7 MB** | **1.35** |
| plane 4 | 978.6 MB | 1,087.5 MB | 0.09 |
| plane 5 | 181.8 MB | 547.8 MB | 0.30 |
| trace map alone | 173.8 MB | 485.9 MB | 0.26 |
| **whole `sdip verify`** | 1,011.4 MB | **2,251.6 MB** | 1.03 |

- **Criterion 1 (reproduces P23): holds.** 2,251,620,352 B against P23's 2,253,045,760 B,
  0.06 % apart.
- **Criterion 2 (attributes the peak): Plane 3 sets it.** Alone, it peaks at 100.1 % of the
  whole command. No memory is held across steps beyond that.
- **Criterion 3 (attributes the growth):** Plane 3 grows at 1.35 MB per MB, more than the whole
  command's 1.03. Plane 5 grows at 0.30 and the trace map at 0.26. Plane 4 after P23 grows at
  0.09: its roughly 1 GB is close to constant in the file.

**What this means for stage B.** Plane 3, the trace-header plane, holds about 5.9 KB of memory
per trace on `large` (2.2 GB over 378,000 traces), for 240 bytes of header per trace. It reads
headers whole, so its working set is many times the bytes it compares. Plane 3 is stage B's
target. Plane 5 and the trace map, which Planes 3, 4 and 5 each build, come second.
